# PDI v1.1.0

PDI v1.1.0 completes the product's local account and security experience and makes deployed component provenance visible from the application.

## Accounts and security

- Optional standards-compatible TOTP 2FA uses a locally rendered QR code and requires authenticator verification before activation. TOTP secrets are encrypted with AES-256-GCM using an operator-managed key available only to the API service.
- Ten one-time recovery codes are shown only at creation or regeneration, stored only as Argon2id hashes, consumed atomically, and distinguished from authenticator login in security audit data.
- Users can change their Argon2id password, inspect and revoke active sessions, revoke all other sessions, and create or revoke existing scoped API tokens. Password changes revoke all previous sessions and rotate the current session and CSRF token.
- Minimal Admin, User, and Read-only roles support user creation, deactivation/reactivation, role changes, 2FA status visibility, and immediate session/token revocation. The last active administrator cannot be deactivated or demoted.

## System information

- Settings → About reports the product, backend, and web versions; backend/web commit and build metadata; Alembic revision; platform and architecture; deployment type; OCR provider and available binary versions; and the configured intelligence provider/model.
- Backend/web version or revision mismatches are reported explicitly. The API exposes only authenticated, operator-safe information.
- Release builds inject the semantic version, exact Git commit, and deterministic commit timestamp into both images and their OCI metadata.
- The locked runtime uses cryptography 50.0.1 and passes the current Python and npm advisory audits.

## Upgrade compatibility

- Database migration required: yes (`20260826_0012`). Existing v1.0.2 users are assigned Admin, and existing sessions and API tokens remain valid.
- Reindex required: no.
- Backup, storage, and export format changes: none.
- Before starting v1.1.0, generate a 32-byte random key, encode it with URL-safe base64, and set `PDI_TOTP_ENCRYPTION_KEY` in the protected `.env.release`. Keep the same key for the lifetime of all enabled TOTP accounts. Loss of the key requires disabling/re-enrolling 2FA through a controlled recovery procedure.
- Rollback should restore the verified pre-upgrade PostgreSQL and document-storage backup together before restarting v1.0.2; do not rely on an application-image-only rollback after the schema migration.

## NAS update verification

Deploy the exact immutable `1.1.0` backend and web digests, never `latest`, using the established preflight and verified-backup workflow. After startup:

```bash
docker compose --env-file .env.release -f compose.release.yaml ps
docker compose --env-file .env.release -f compose.release.yaml exec -T api pdi readiness
docker compose --env-file .env.release -f compose.release.yaml exec -T api pdi search verify
docker compose --env-file .env.release -f compose.release.yaml exec -T api pdi storage reconcile
```

Then sign in with the existing administrator, confirm Settings → About reports v1.1.0 with matching backend/web metadata and Alembic `20260826_0012`, enable and validate 2FA on a disposable test account, test a one-time recovery code, revoke a disposable session/token, and verify one existing document and search result. No production NAS access is part of release preparation.
